# Appliance Energy Forecasting

A time-series case study comparing five benchmark models, SARIMAX, a tuned XGBoost
feature-based model, and a genuine Chronos-2 foundation-model forecast, on the UCI
**Appliances Energy Prediction** dataset.

## Project aim

Forecast short-term household appliance energy use and evaluate whether
increasingly complex models actually improve on simple benchmarks, and by how much.

## Key result

Every model is evaluated with a genuine **rolling 24-hour forecast**: 14 separate
forecasts across the held-out 14-day test period, each built only from history that
would truly be known at that point (never a model's own prior output). Final ranking:

| Model | MASE | Notes |
|---|---|---|
| **XGBoost (tuned)** | **0.548** | Best overall, but see the conditional-forecast caveat below |
| **Chronos-2** (real, zero-shot) | **0.614** | Genuinely blind, no covariates, no tuning |
| **SARIMAX(1,0,3)×(1,1,1,24)** | 0.689 | |
| Seasonal naive (weekly) | 0.813 | Strongest simple benchmark |
| Seasonal naive (daily) | 0.904 | |
| Mean | 0.941 | |
| Naive / Drift | 1.60 / 1.61 | |

MASE below 1.0 means the model beats the in-sample seasonal naive error scale.
Full metrics: `outputs/metrics/model_comparison.csv` (generated by notebook 07).

**Important caveat**: XGBoost's and SARIMAX's results use the *true, realized*
indoor sensor and outdoor weather values for each forecast day, not forecasts of
them, a real deployment wouldn't have these in advance. These should be read as
**conditional forecasts**. Chronos-2's result is target-only and carries no such
caveat, see `notebooks/07_model_comparison.ipynb`, Part 9, questions 4-6, for the
full discussion and the resulting deployment recommendation.

## Dataset

**Appliances Energy Prediction** (Candanedo et al., 2017), retrieved from the UCI
Machine Learning Repository:
`https://archive.ics.uci.edu/ml/machine-learning-databases/00374/energydata_complete.csv`

19,735 rows at 10-minute resolution, resampled to hourly (3,290 rows) by every
notebook that needs it. No missing values in the raw data.

### Why both notebooks *and* `src/`

The seven notebooks are each **self-contained** (every function they need is defined
inline, and each downloads/rebuilds the processed data itself if it isn't already
present locally). This was a deliberate choice: it means any single notebook can be
opened on its own in Colab, or anywhere else, and just run, with no import errors
from a missing local package. They are the authoritative, fully-executed record of
this project, every number in this README was pulled directly from their real
outputs.

`src/appliance_energy/` extracts that same logic into a proper, tested Python
package, for the "reusable code" and code-quality side of the brief, and it is not
just a code-quality nicety, `scripts/run_pipeline.py` genuinely runs the full
analysis through this package end to end (see below), so the core logic (data
cleaning, benchmarks, SARIMAX, the feature-based model, evaluation metrics,
Chronos-2 calls) is independently tested and independently runnable, not just
"it worked when I ran the notebook."

## Installation

```bash
python -m venv .venv
source .venv/bin/activate      # .venv\Scripts\activate on Windows
pip install -r requirements.txt
```

`torch` and `chronos-forecasting` (needed only for the foundation model, notebook
06 and `models/foundation.py`) are listed separately in `requirements.txt`, they're
a larger install and only required if you're re-running that part. `torch`'s
default install pulls in GPU/CUDA dependencies (400MB+) even though nothing in this
project uses a GPU; if the install is slow or unreliable on your connection, the
CPU-only build is much smaller and sufficient here:
```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install chronos-forecasting
```

## Running things

**The notebooks** (primary path): open any of `notebooks/01` through `07` in
Jupyter or Colab and run top to bottom. Notebooks 04-06 save their forecasts to
`outputs/forecasts/`; notebook 07 reads those back in to build the final
comparison, so run 04, 05, and 06 before 07, in the same session/working
directory (07 also includes a manual-upload fallback cell if you're running it in
a separate Colab session from the others).

**The pipeline script** (full analysis, runnable from a fresh clone):
```bash
python scripts/run_pipeline.py
```
Runs all 10 steps end to end: load/clean the data, build the feature table, split
train/test, fit all five benchmarks, SARIMAX, the XGBoost feature model, and
Chronos-2 (all with genuine rolling 24-hour forecasts), evaluate everything, and
save forecasts/metrics/a comparison plot to `outputs/`. By default it uses the
already-selected SARIMAX order and already-tuned XGBoost hyperparameters (both
found once via the slower searches in notebooks 04 and 05) rather than re-running
those searches. Pass `--full-search` to redo both from scratch:
```bash
python scripts/run_pipeline.py --full-search
```
If Chronos-2 can't be loaded (missing packages, or no internet access to Hugging
Face), the script reports that clearly and continues without it, it does not
substitute a placeholder result under the `foundation_model` name.

**Tests**:
```bash
pytest tests/ -v
```
17 tests covering no-leakage guarantees on lag/rolling features, MASE correctness,
rolling-forecast history isolation (each day's forecast provably can't see its own
or a later day's real values), and basic data-cleaning correctness.

## Known limitations

- **SARIMAX grid search range**: the brief specifies a full search over
  p=[0,6], d=[0,2], q=[0,6]. The search actually run by default (`notebooks/04`,
  and `scripts/run_pipeline.py` unless `--full-search` is passed) covers a reduced
  range (p, q in [0,3], d fixed at 0, justified by the stationarity result from
  notebook 02) for compute-time reasons on a single CPU core, documented in that
  notebook. Running the full grid remains an option, not the default.
- **Conditional forecasts**: see the caveat under Key Result above.
- See `notebooks/07_model_comparison.ipynb`'s "Limitations and future improvements"
  section for the complete list (genuine day-ahead weather forecasts, XGBoost
  uncertainty estimates, a second foundation model, ensembling).
